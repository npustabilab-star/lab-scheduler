# 改用學號登入 — 設計補充

日期：2026-11-25
狀態：已定案（使用者於 2026-11-25 確認）
修改對象：`2026-11-24-lab-scheduler-design.md` 的 4.1（帳號與登入）、4.9（通知）、4.10（交接）

---

## 1. 為什麼改

不使用 Google 帳號，改成「學號＋密碼」登入；只有老師或學長預先加入名單的學號才能登入。

## 2. 使用者確認的決定

- 登入方式：學號＋密碼。
- 初始密碼：學號後四碼。
- 只有管理者加入名單的學號能登入。
- 通知信：新增成員時另外填 Email；沒填的人只收得到網站內的通知（鈴鐺），不寄信。

## 3. 行為

### 3.1 登入
- 登入頁只有「學號」與「密碼」兩欄，移除 Google 登入。
- 不在名單、或密碼錯誤，一律顯示「學號或密碼錯誤」（不透露學號是否存在）。
- 已停用的帳號不能使用系統（顯示「帳號已停用」）。
- *（我的決定）* **第一次登入強制改密碼**：初始密碼可被猜到，因此帳號在改密碼之前，除了「設定新密碼」頁之外什麼都看不到——這條規則在資料庫層級執行（未改密碼的帳號視同未啟用），不只是前端擋。
- *（我的決定）* 新密碼至少 8 碼，且不可等於學號後四碼。

### 3.2 管理頁
- 「待審核」改為「新增成員」：學號、姓名、身分（研究生／專題生）、專題生須選指導研究生、Email（選填）。新增後該學號立即可用後四碼登入。
- 成員清單新增：「重設密碼」（密碼回到學號後四碼，下次登入需再改）、編輯 Email。
- 停用、更換指導研究生、設為管理者等既有功能不變。
- 學號不可重複；新增重複學號顯示「這個學號已經在名單中」。

### 3.3 通知
- 站內通知（鈴鐺）不變。
- Email 只寄給有填 Email 的人；沒填的跳過，不算錯誤。
- *（我的決定）* 老師帳號建立時必須填 Email，確保收得到「待你確認」。

### 3.4 第一位管理者（老師）
- *（我的決定）* 老師沒有學號，使用一組自訂代碼（例如 `teacher`）當登入帳號；初始密碼由建立的人設定並轉告。由部署的人用一個指令建立（寫進交接文件），之後老師即可在管理頁新增其他人。

## 4. 做法（Approaches）

| 做法 | 內容 | 取捨 |
|---|---|---|
| **A. 沿用 Supabase Auth 的帳密登入（採用）** | 每個學號對應一個 Supabase 使用者；登入帳號是由學號組成、不會收信的內部 email；新增成員與重設密碼由一支只允許管理者呼叫的 Edge Function 執行 | 密碼由 Supabase 安全地雜湊保存，登入、工作階段、RLS 全部沿用現有架構，改動最小 |
| B. 自建學號／密碼表 | 自己存密碼雜湊、自己發登入憑證 | 要自己處理密碼安全與工作階段，風險高、工作量大，排除 |

## 5. 技術決定（我的決定，供開發者參考）

- 每個成員的 Supabase 登入 email 為內部格式 `<學號>@users.lab-scheduler.internal`（只用來登入，系統不寄信到這裡）；關閉 Supabase 的公開註冊與 email 確認。
- Supabase 規定密碼至少 6 碼；前端送出密碼時一律在前面加上固定前綴，使用者感覺不到（四碼初始密碼因此可用）。
- `profiles` 新增：`student_id`（唯一、必填）、`notify_email`（可空）、`must_change_password`（布林）。原本的 `email` 欄位不再作為通知信箱。
- 新 Edge Function `admin-members`：驗證呼叫者是有效管理者後，以 service role 建立使用者／重設密碼，並寫入 profile。
- `is_active_member()` 對 `must_change_password = true` 的帳號回傳 false；改密碼後由 RPC 清除旗標。
- 寄信函式改讀 `notify_email`，為空則跳過。
- 移除 Google OAuth 設定與交接文件中相關步驟；交接文件改寫「建立第一位管理者」與「重設密碼」。

## 6. 非目標

- 自助「忘記密碼」寄信重設（由管理者重設即可）。
- 學校單一登入。
- 讓成員自己修改 Email（由管理者修改）。
