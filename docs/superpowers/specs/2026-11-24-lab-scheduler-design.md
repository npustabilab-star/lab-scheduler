# 研究室排班與預約系統 — 設計文件

日期：2026-11-24
狀態：已定案（使用者於 2026-11-24 確認）

---

## 1. 目的與原因

研究室需要一個系統解決三件事：

1. **值班表**：知道週一到週五每一節是誰待在實驗室。目前是每個人依自己的課表決定哪幾節能來，系統要讓大家自己填、即時彙整成總表，並在「某天完全沒人」時提醒。
2. **行事曆**：用月曆／週曆一眼看到值班與會議安排。
3. **開會預約**：大學部專題生需要跟「老師＋帶他的研究生」約時間討論專題，至少提前一週預約，並由老師與研究生確認。

成功的樣子：學期初每個研究生登入勾完自己的格子，總表自動成形；專題生不用再私訊來回喬時間，在系統裡挑一個三方都可行的時段送出，老師和學長姐按同意就成立。

## 2. 目標、非目標、反目標

**目標**
- 每人登入後只能編輯自己的班表，編輯後即時同步到總表（其他人畫面不需重新整理）。
- 總表與行事曆清楚顯示每節／每天誰在，並標出整天無人的日子。
- 專題生只能看到並選擇「真的可行」的時段（老師開放 ∩ 指導研究生有值班 ∩ 未被預約 ∩ 至少 7 天後）。
- 預約需老師與研究生都同意才成立，並有系統內通知與 Email 通知。
- 手機與電腦都能用，校內外都能連。

**非目標（這一版不做）**
- 串接學校單一登入（SSO）。
- 手機 App（用網頁即可，需支援手機版面）。
- 打卡、出勤紀錄、統計時數。
- 會議室／儀器預約。
- LINE / Slack 等其他通知管道。

**反目標（就算功能都能動，出現這些就算失敗）**
- 系統難以維護、交接，做的人畢業後就沒人能接手。
- 有人能改到別人的班表或別人的預約。
- 同一個時段被兩個專題生同時約到（雙重預約）。
- 專題生看到可選的時段，送出後才發現其實不可行。

## 3. 角色

| 角色 | 能做的事 |
|---|---|
| **老師** | 設定自己的「可約時段」格子；確認／拒絕／取消預約；看總表與行事曆；具管理者權限。 |
| **研究生** | 填自己的值班格子；標記某一天臨時不在；確認／拒絕／取消與自己相關的預約；看總表與行事曆。 |
| **專題生** | 不排班；預約與老師＋指導研究生的會議；取消自己的預約；看行事曆。 |
| **管理者**（權限，非獨立身分） | 審核新帳號、指定角色、指定專題生的指導研究生、設定學期與節次時間、標記停課日。預設是老師，老師可再把管理權限給某位研究生。 |

- 一位專題生對應一位指導研究生。一位研究生可以帶多位專題生。
- 研究室只有**一位老師**（使用者確認），系統不需要支援多位老師。
- 專題都是**個人**做，不分組（使用者確認）。每場會議只有一位專題生。

## 4. 功能細節

### 4.1 帳號與登入
- 使用 Google 帳號登入（Supabase Auth）。
- 第一次登入的人會建立「待審核」帳號，看不到任何資料，直到管理者核准並指定角色（專題生還要指定指導研究生）。
- *（我的決定）* 不自建帳號密碼，避免忘記密碼等維護工作。
- *（我的決定）* **停用帳號**：管理者可以把畢業或離開的人設為「停用」。停用後不能登入，歷史資料保留（舊學期仍查得到），他未來的值班格子不再計入，未來的待確認或已成立預約一併取消並通知相關人。

### 4.2 學期與節次設定（管理者）
- 學期：起訖日期。值班格子以「學期」為單位，換學期時大家重新填，舊學期資料保留可查。
- 節次：每天固定 8 節，管理者可設定每節的起訖時間（例如第 1 節 08:10–09:00），用於行事曆顯示與 Email 內容。
- 停課日：管理者可以標記國定假日、校慶等日期。這些天不算值班，也不能預約，「整天無人」也不提醒。

### 4.3 值班表（研究生）
- 每人一張「週一～五 × 第 1～8 節」的格子，點一下切換「在／不在」。
- 格子代表**整學期每週固定**的安排。
- **單日例外**：在行事曆上點某個日期，可以把自己那天標成「不在」（整天或指定節次），只影響那一天。
- 編輯後立即存檔並即時推送給所有正在看總表或行事曆的人。

### 4.4 總表
- 同一張「週一～五 × 8 節」格子，每格列出該節在的人名（或人數，點開看名單）。
- 某個「星期幾」所有人加起來一節都沒勾時，整欄標紅。
- 總表只顯示每週固定的安排。單日例外反映在行事曆上。

### 4.5 行事曆
- 月檢視與週檢視。
- 每一天顯示：當天值班的人與節次（已套用單日例外）、當天的會議。
- **整天無人的日期標紅**：套用例外後，那天沒有任何研究生任何一節在，且不是停課日。
- 會議顯示規則 *（我的決定）*：已成立的會議所有人都看得到（誰、何時）；待確認的會議只有相關的三個人看得到。

### 4.6 老師可約時段
- 老師有一張自己的「週一～五 × 8 節」格子，勾選可以被約的節次，整學期固定。
- 老師也可以在行事曆上把某一天標成不開放（單日例外），規則同研究生。

### 4.7 開會預約（專題生）
- 一場會議 = 一節課的長度，參與者固定為：專題生、老師、該專題生的指導研究生。
- **可選時段**是同時滿足以下條件的「日期＋節次」：
  1. 日期 ≥ 今天 + 7 天，且在本學期內、不是停課日；
  2. 老師那節有開放（已套用單日例外）；
  3. 指導研究生那節有值班（已套用單日例外）；
  4. 老師在那節沒有其他待確認或已成立的會議；
  5. 指導研究生在那節沒有其他待確認或已成立的會議。
- 專題生選一個時段，可附一句說明（例如要討論什麼），然後送出 → 狀態變成「待確認」，該時段立刻被保留。
- 資料庫層級要保證不會雙重預約：同一位老師、同一日期節次，只能有一筆非取消的預約，研究生也一樣。
- **每位專題生同時只能有一筆預約**（使用者確認）：只要他有一筆「待確認」或「已成立」、會議時間還沒過的預約，就不能再約新的。預約頁改成顯示目前這一筆和它的狀態。會議結束、被拒絕、被取消或逾期後，才能再約。這條規則也要在資料庫層級保證。

### 4.8 確認流程
- 狀態：`待確認` → `已成立` / `已拒絕` / `已取消` / `已逾期`。
- 老師與研究生**都按同意**才變成「已成立」。
- 任一人按拒絕（可附原因）→ 「已拒絕」，時段釋放，專題生收到通知後可以重新選。
- *（我的決定）* 會議日前 3 天仍未兩人都同意 → 自動變成「已逾期」，時段釋放，三方都收到通知。
- 「已成立」的會議，三人中任何一人都可以取消（可附原因），其他兩人收到通知。
- *（我的決定）* **任何會讓既有預約變得不可行的變更，都用同一套「先警告、再取消」流程**：系統先跳出警告，列出受影響的未來會議（待確認與已成立），使用者確定後，變更生效，這些會議一併取消並通知相關人。適用的變更：
  - 研究生或老師把某天標成不在（單日例外）；
  - 研究生取消每週值班格子的某一節，或老師取消每週可約格子的某一節；
  - 管理者新增停課日；
  - 管理者更換某位專題生的指導研究生；
  - 管理者停用某個帳號。
  已經過去的會議不受影響。

### 4.9 通知
- **系統內通知**：右上角鈴鐺顯示未讀數。事件包括新預約待確認、預約成立、被拒絕、被取消、逾期。
- **Email**：上述事件同時寄給相關人。尤其要確保老師收到「新預約待確認」。
- *（我的決定）* 寄信由 Supabase Edge Function 透過**研究室專用 Gmail 帳號的 SMTP**（應用程式密碼）寄出。理由：Resend 等服務的免費方案需要自有網域並設定 DNS 才能寄給任意收件人，研究室不一定有。Gmail 免費額度（每日數百封）對研究室綽綽有餘。之後如果有網域，可以改用寄信服務。

### 4.10 帳號歸屬與交接
- *（我的決定）* Supabase、網頁託管、寄信用的 Gmail，全部掛在**同一個研究室共用的 Google 帳號**底下，不綁在任何個人帳號上。交接時只要移交這個帳號的密碼與兩步驟驗證。這個帳號需要由研究室自行建立。
- 專案需附一份簡短的交接說明：如何登入後台、如何恢復暫停的 Supabase 專案、如何開新學期、如何更換寄信密碼。

## 5. 做法選擇（Approaches）

| 做法 | 內容 | 取捨 |
|---|---|---|
| **A. 網頁 + Supabase（已選）** | React 前端；Supabase 提供資料庫、登入、即時同步、伺服器函式；放在免費網頁託管 | 要寫的程式最少、最好交接、免費方案夠用、校內外都能用。資料放在外部服務；免費方案連續 7 天沒人使用會暫停（例如寒暑假），需要進後台手動恢復。 |
| B. 實驗室自架伺服器 | 自寫後端 + 資料庫 + 登入 + 即時推送 + 寄信 | 資料留在校內、彈性大；但工作量約多一倍、需要長期維護主機、校外連線要另外處理，畢業交接風險高。 |
| C. Google 試算表 + 日曆 | 用現成工具拼湊 | 成本最低，但「只能改自己的」、「兩人確認」等規則做不乾淨，被排除。 |

**使用者選擇 A**。理由：研究室系統最大的風險是沒人維護，A 要維護的東西最少，而且登入、即時同步、寄信都有現成功能。

## 6. 技術決定

- 前端：React + TypeScript（Vite），介面使用繁體中文，支援手機版面。
- 後端：Supabase
  - Postgres 資料庫，用 Row Level Security 做權限控管（只能改自己的格子、只能操作與自己有關的預約）。
  - Auth：Google 登入。
  - Realtime：值班格子、例外、預約狀態的變更即時推送。
  - Edge Functions：寄 Email、處理逾期自動取消的排程。
- 防雙重預約：用資料庫的唯一性限制（部分唯一索引，排除已取消／已拒絕／已逾期的預約）處理，不只靠前端檢查。
- 「至少提前 7 天」和「可選時段」的規則要在伺服器端（資料庫函式或 Edge Function）再驗證一次。
- 時區固定為 Asia/Taipei。

## 7. 資料模型（概略）

- `profiles`：使用者、角色（teacher / grad / undergrad）、帳號狀態（待審核 / 啟用 / 停用）、是否管理者、指導研究生 id（專題生用）、Email。
- `semesters`：起訖日期、是否為目前學期。
- `periods`：第 1～8 節的起訖時間。
- `no_class_days`：停課日。
- `weekly_slots`：(使用者, 學期, 星期幾, 節次)：研究生的值班格子與老師的可約格子共用這張表。
- `slot_exceptions`：(使用者, 日期, 節次或整天)：單日不在。
- `bookings`：專題生、老師、研究生、日期、節次、說明、狀態、老師是否同意、研究生是否同意、拒絕或取消原因、時間戳記。
- `notifications`：收件人、類型、相關預約、已讀與否。

## 8. 留給開發者決定的事

- 網頁託管平台（Vercel、Cloudflare Pages、Netlify 擇一）。
- UI 元件庫與行事曆元件的選擇。
- 專案資料夾結構、測試框架。
- Email 模板的文字與樣式。
- 逾期檢查的排程頻率與確切截止時刻。
- 開新學期時是否提供「複製上學期格子」的捷徑。

## 9. 決定紀錄

**使用者確認**
- 值班以「週一～五 × 8 節」為單位，依個人課表自選，整學期固定，可單日請假。
- 每天只要有任一人來過就算有人；整天無人才提醒。
- 要登入才能選班，自己編輯後即時同步到總表。
- 開會對象是老師＋指導研究生，至少提前一週預約，需兩人都確認。
- 只有一位老師；專題為個人；每位專題生同時只能有一筆預約。
- 做法選 A（網頁 + Supabase）。

**我的決定（請檢查）**
- Google 帳號登入，新帳號需管理者審核；管理者預設為老師。
- 停課日由管理者標記。
- 已成立的會議全員可見，待確認的只有相關三人可見。
- 會議日前 3 天仍未兩人都同意就自動逾期。
- 任何讓既有預約失效的變更，都走「先警告、再取消並通知」。
- 停用帳號：保留歷史，取消未來的預約。
- 用研究室專用 Gmail 寄信；所有服務掛在同一個研究室共用帳號下。
